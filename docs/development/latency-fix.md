# 0.3.2 鬆鍵延後與輸入延遲修正

## 可重現的程式問題

原本 VirtualOutput 以 256 份容量 FIFO 依次傳送每份實體狀態。測試模擬短暫消費端背壓，先連續提交 100 份 ZR 按住、再提交鬆開。原碼確實失敗：直到第 101 份才讀到鬆鍵；修正後第 2 份即讀到鬆鍵。這證明程式中的積壓風險，不代表已完整重現特定遊戲當時的無線環境。

## 實作

- 即時緩衝合併相同數位按鍵狀態下的重複／類比樣本，保留最新搖桿及體感；ZL／ZR 的零／非零轉換，以及各按鍵邊緣保留順序。
- 正常的快速按下／鬆開依序傳送。若最早等待狀態已超過 40 ms，直接收斂到最新狀態；若最新樣本也已過期，送中立狀態，避免重播過時操作。在這種壅塞下可能略過短操作，會記入 StaleDropped。
- 不將過期或反向時間戳的通知偽裝成新輸入。Switch 2 使用原本 Windows BLE 通知／USB 讀取完成的 QPC；其他裝置暫用 facade 收到狀態的時間。
- 150 ms 沒有新實體輸入時，先送一次中立狀態清空所有按鍵、扳機與搖桿。新資料到達才恢復輸入。這與約 2 秒的連接中斷判斷分開，短暫斷流不必等兩秒才鬆鍵。
- 非同步寫入有 100 ms 取消期限；不同按鍵邊緣超過 32 份則明確停止連接，避免無上限積壓或只悄悄遺失鬆鍵。
- 所有時間是管理程式預算，不是硬即時或端到端延遲保證；Windows 排程、休眠及驅動仍可能延後執行。

## 診斷

匯出診斷加入 OutputStatistics（佇列最大深度、合併、過期略過、保護中立、寫入耗時與逾時），並保留 ZL／ZR 狀態。斷開後仍保存最後一次輸出統計。

開發模式可用 `--hardware-live <report-path> --bluetooth --manual-latency`，在首頁手動開始 30 秒測試，將觸發鍵輸入與 Windows XInput 讀回比對。量測不改偏好、不啟用音訊，也不安裝或修改驅動。`--manual-latency` 僅是診斷入口，一般介面不顯示此按鈕。

量測期間請保持視窗可見。量測暫時以 timeBeginPeriod(1) 請求本程序計時精度，finally 配對 timeEndPeriod；正常橋接不作此請求。依據 [Microsoft 文件](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod)，Windows 11 視窗被遮蔽或最小化時不保證維持請求的精度，因此結果另列實際輪詢間隔。

這不是手指按下到遊戲畫面的延遲；未觀測到的轉換表示量測無法分辨，不直接當作裝置丟包。

## 證據

- 原流程的 101 份封包鬆鍵重現測試先失敗，再修正通過。
- 自身檢查涵蓋：新鮮 ZL／ZR 邊緣順序、快速點按、最新搖桿、過期歷史、原始通知時間、斷流中立與恢復、實際 writer 在背壓後送鬆鍵，以及堵塞寫入停止。
- 上游原生時戳、BLE 輸入／排空、USB 回饋與退出等 181 項測試通過。
- 第一輪藍牙 Xbox 讀回觀測到 57 次無歧義轉換（28 次鬆鍵），另有 1 次輪詢未分辨的轉換；最大排隊深度 1、0 過期略過、0 溢位、0 寫入逾時，單次寫入最大約 1.54 ms。當輪觀測鬆鍵最長約 15.64 ms，但請求 2 ms 的預設輪詢受到約 15 ms 的排程影響，此值不當作精準的實際輸出延遲。

- 較高精度的第二輪：實際輪詢 P95 約 3.064 ms；觀測 62 次無歧義變化、31 次鬆鍵，未觀測／歧義均為 0。程式收到狀態到 XInput 讀回的鬆鍵 P95 約 3.010 ms、最大約 3.450 ms；Windows 通知到程式最大約 0.150 ms。這是新版的讀回觀測，不與第一輪較粗的量測直接比較，也不當作藍牙／遊戲端到端延遲。

《異環》駕駛時的長時間實際體感仍需使用者驗收；不將離線重現或短時間 XInput 讀回當作所有遊戲問題已排除的證據。
